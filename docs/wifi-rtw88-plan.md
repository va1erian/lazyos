# Wi-Fi on the AMD NUC: the RTL8822CE driver

> **Status: in progress, revision 1 (2026-10-11).** The driver half of
> Wi-Fi for the one real machine LazyOS targets today. Builds on
> [wifi-prerequisites-plan.md](wifi-prerequisites-plan.md) (WP0-WP3 built:
> crypto, multi-NIC `netd`, `keyd` secrets, `libs/ieee80211`, `libs/eapol`)
> and replaces [wifi-plan.md](wifi-plan.md)'s chip choice for this machine.

## 1. The card

The NUC ([compat/amd-nuc](compat/amd-nuc/README.md)) carries a Realtek
**RTL8822CE** (`10ec:c822`, PCI class 0x0280, M.2, 802.11ac 2x2, BT combo
over USB), Linux driver `rtw88_8822ce`. From its survey: BAR 2 is 64 KiB of
MMIO, MSI (one vector, 64-bit capable) is offered, ASPM L1 is enabled by the
firmware, the link is PCIe gen 1 x1.

wifi-plan.md chose the MT7925 for a USB dongle; this machine has no dongle
and a PCIe card, so the chip changes and two of that plan's assumptions with
it:

| wifi-plan assumption | RTL8822CE reality | Consequence |
|---|---|---|
| Firmware converts 802.3 to 802.11 (encap offload) | It does not: the host builds 802.11 data frames (QoS header, LLC/SNAP) and strips them on receive | The driver side converts in software, through fuzzed `libs/ieee80211` functions, so the DMA-holding process still parses nothing it could get wrong unchecked |
| Firmware scans | Scan offload exists only in newer firmware and is not used by Linux for this chip by default | The driver steps channels and sends probe requests itself |
| Hardware CCMP with hardware IV | Hardware CCMP, but the **IV (PN) is generated by software** (`IEEE80211_KEY_FLAG_GENERATE_IV`) and replay checks are software | The soft-MAC layer keeps the TX PN and checks the RX PN |
| USB bus | PCIe: buffer-descriptor rings, MSI | No USB device interface (WP6 section 3.9) is needed for this machine |

## 2. Licence

Every file of `drivers/net/wireless/realtek/rtw88` that this driver follows
is `GPL-2.0 OR BSD-3-Clause` (checked at `torvalds/linux`
`d6d3455d8751`, 2026-10-11: all 37 files read carry that tag). LazyOS takes
it under **BSD-3-Clause**, wifi-plan section 4 option A unchanged: a Rust
translation, each module naming its upstream file, `THIRD_PARTY.md`
carrying Realtek's notice. The firmware `rtw88/rtw8822c_fw.bin` comes from
linux-firmware under `LICENCE.rtlwifi_firmware.txt` (redistribution in
binary form permitted): a separate file on the OS volume, fetched and
hash-pinned, never `include_bytes!`. `mac80211`/`cfg80211` stay unread.

## 3. Architecture

```
 netd ◄─nic.v1─┐                       ┌─► wlanmd ◄─► keyd
               │                       │   (MLME, EAPOL, profiles)
               │     wifi.hw.v1 ◄──────┘
        ┌──────┴───────────────────────────┐
        │ soft-MAC layer (libs/wifimac)    │  shared by wifid and wifisim:
        │  hw.v1 + nic.v1 servers,         │  scan stepping, frame classes,
        │  802.3 <-> 802.11, CCMP PN       │  CCMP header and replay
        └──────┬──────────────────┬────────┘
          Radio trait        Radio trait
               │                  │
        wifid: libs/rtw88    wifisim: 802.11 in Ethernet
        (PCIe, MSI, DMA,     over a second virtio-net
         CAM, firmware)      card, software CCMP
               │                  │
          RTL8822CE          tools/wifi/fake_ap.py (CI)
```

- **`libs/rtw88`**: the chip, `no_std`, host-tested against a fake bus.
  Mirrors upstream's split (`hci`, `mac`, `fw`, `efuse`, `sec`, `tx`, `rx`,
  `pci`, `phy`, `rtw8822c`, `coex`), see its crate docs.
- **`libs/wifimac`**: what both radio programs share, over a `Radio` trait
  (tune, transmit an 802.11 frame, keys, BSSID and filters, received frames
  with signal and decryption status).
- **`wifid`** (uid `_wifi` 911, `CAP_DEV_CLAIM`): claims the PCI function,
  maps BAR 2, allocates DMA, arms MSI, loads the firmware from
  `fhs::FIRMWARE`, and runs `wifimac` over `rtw88`. Registers `wlan0`.
- **`wifisim`** (uid `_wifisim` 913) and **`wlanmd`** (uid `_wlan` 912) are
  WP4 of the prerequisites plan.

## 4. Stages

| Stage | Deliverable | Evidence |
|---|---|---|
| **R0** Plumbing | firmware fetch + `fhs::FIRMWARE` + `libs/fwload`; `LAZYOS_WIFI=1`; `devd` row for `10ec:c822`; `run_demo.py --wifi`, GUI; `THIRD_PARTY.md` | `cargo test -p fwload -p devmatch`; the file lands at its path with its licence |
| **R1** Chip library | `libs/rtw88`: power on, firmware download, MAC/BB/RF init, channel switch, TX/RX descriptors, PCIe rings, CAM | host tests against the fake bus, sequences compared with upstream's |
| **R2** Station stack on the simulator | WP4: `wlanmd`, `wifictl`, `libs/wifimac`, `wifisim`, `fake_ap.py` | `tools/wifi/sim_run.py`: scan, open and WPA2 joins, DHCP and echo over `wlan0` |
| **R3** First light on the NUC | `wifid` up to firmware running and MAC address read | `WIFID:FW:READY`, `WIFID:MAC:<addr>` over `dbgd` |
| **R4** Scan on the NUC | channel switching, RX of beacons | `wifictl scan` lists the home networks |
| **R5** Join on the NUC | auth/assoc, 4-way, CAM keys, data | DHCP lease and `ping` over `wlan0` |

## 5. The test loop on the NUC

There is no serial port and no emulated RTL8822CE. The loop is a stick image
built with `LAZYOS_WIFI=1 LAZYOS_NETD=1 LAZYOS_DBGD=1 LAZYOS_DBGD_CONTROL=1`
(wired Ethernet stays up through the RTL8168 for `dbgd`), booted once, then
`dbgctl reload wifid` after each rebuild: `init` restarts the driver from the
new binary and rolls it back if it dies. `log --follow` shows `WIFID:*`.
`wifid` prints a register dump of the MAC's key registers on any bring-up
failure so a failed boot is diagnosable from the log alone.
