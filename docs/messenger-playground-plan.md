# Plan: Messenger Playground

**Goal:** a desktop app where anyone can *see* what Messenger offers, *listen*
to it, and *poke* it, without leaving the window or knowing the wire format.
Three activities, one screen:

1. **Browse** every interface (methods, structs, enums, topics, with their doc
   comments) and see which of them are being served right now, by whom.
2. **Listen** to topics: declared ones and live ones, decoded with the type the
   IDL gives them, with the broker's QoS choices visible and the delivery
   counters on screen.
3. **Do** things: write Rhai against the `msg` module and the generated
   `sys::*` modules in an editor, run it, stop it, and see output and errors
   in place. Every click in the browser can turn into a script line; nothing
   happens behind the user's back.

It is a teaching tool and a debugging tool at once. [`fabricmon`](../xui-app/src/bin/fabricmon.rs)
shows *that* the fabric is busy; the Playground shows *what* is on it and lets
you answer.

**Non-goals.** No new Messenger interface for the app itself (a toy interface
for the examples is optional, P4). No second scripting language. No packet
capture or per-transaction tracing (`docs/messenger.md` section 13 says those
do not exist and are not planned). Not an IDE: LazyRAD stays the place for
apps with forms.

Status: **implemented in this worktree, uncommitted** (see "As built" at the end); verified in a QEMU guest by `python tools/playground/run.py`. D1 is decided: the Terminal's authority, as
a **developer-tool package**, the class defined in
[`devtool-packages-plan.md`](devtool-packages-plan.md), with its risks stated
(D1, D7). Issue: TBD.

## 1. What already exists (and so is reused, not rebuilt)

| Need | Exists | Where |
|---|---|---|
| Every interface as data: methods with docs, params, returns, structs, enums, declared topics (pattern, payload, QoS, retained) | `msg::interfaces()` table, generated by `midlc --schema` | `libs/rhai-lazy/src/msg/{idl,schema}.rs` |
| Text description of an interface | `msg::describe(name)` | `libs/rhai-lazy/src/msg/mod.rs` |
| Value codec both ways (Rhai value <-> TLV) | schema codec, cross-checked against the compiled one | `libs/rhai-lazy/src/msg/codec.rs` |
| Typed, documented script API per interface | `sys::<alias>::*` modules | `libs/rhai-lazy/api/` (`README.md` is the index) |
| Running scripts, `msg::serve`, `msg::on`, `msg::run` | the `rhai` command | `rhai-host/`, `docs/rhai/msg.md` |
| What is registered right now, who owns it | registry `List` (name, owner slot, interface ids, `owner_uid`, `owner_label`, `owner_session`) | `idl/registry.midl`, `xui_app::fabric::registry()` |
| Topics the broker has seen, subscriber counts, retained flag; `Stats` per subscription; `Bell` doorbell | `os.lazy.messenger.topics.v1` | `idl/topics.midl`, `xui_app::fabric::Broker` |
| Rhai-highlighting code editor widget with diagnostics markers | `xui-code-editor` (`rhai-syntax` feature) | `xui-app/crates/code-editor` |
| Markdown on a Blitz view | `xui-docs` | `docs/xui-docs.md` |
| Per-interface reference with a *Permissions* column per topic | `docs/idl/*.md`, shipped to `/docs/os/idl/` | `tools/midlc`, `build_support/docs_embed.rs` |
| A way to derive an app's permissions from its scripts | `rhai_lazy::msg::permissions` (what Make LazyOS App uses) | `libs/rhai-lazy/src/msg/permissions.rs` |

The schema table is the spine: it is generated from `idl/`, so the Playground
can never document an interface that does not exist or miss one that was just
added. A new `.midl` file appears in the browser, in the call form and in the
snippet generator at the next regeneration, with no Playground change.

## 2. Decisions

**D1. Authority: the user's own, as a developer-tool package (decided).**
The app exists to exercise the logged-in user's authority, so it cannot be
confined to a fixed manifest, and it does not try to be. It is a package of
`kind = "developer-tool"` (`devtool-packages-plan.md`): it runs under the label
`tool:os.lazy.playground`, whose Messenger rules are default allow minus a short
reviewed deny list (credentials, sockets unless declared, the dev-spawn scope),
and its children, including the `rhai` it starts, keep that label. What a
script can do is therefore close to what typing `rhai` in the Terminal gives,
and refusals (`EACCES`, `ENOSYS`, an `elevd` prompt for a privileged change) are
shown verbatim, which is itself documentation. Because that is real power, D7
says how the app presents itself and what it risks; the shared pieces (strip,
title, risk table, review gate) come from `xui_app::devtool`.

Differences from the Terminal, all deliberate for v1: it cannot use the
credential services, cannot install packages or approve `elevd` on its own
(`pkgd` refuses labelled callers), and opens no sockets. In exchange it is
attributed, audited, installable as a package and revocable (by `pkgd`; no Settings button yet), and
no new "not a package" exception is added.

Considered and set aside:

* **Unlabelled, like the Terminal.** Simplest, but a fifth entry in the "not a
  core package" list, no attribution (a toast would say "Terminal"), no
  revocation and no shared warning. This was the previous decision of this plan;
  the developer-tool class replaces it.
* **A package with a broad manifest.** Scripts could do only what the manifest
  lists, and the 256-rule limit, the per-segment topic rule and the app-domain
  rule for serving names take away most of what the app is for. Making that
  pleasant needs permission *classes* and IDL access tags, kept in
  [`permission-classes-plan.md`](permission-classes-plan.md), shelved.
* **A per-script derived label** approved on the Installer's development
  consent. Principled, but a `pkgd` path for non-package scripts is a project of
  its own.

**D2. A Rust xui app, not a LazyRAD form.** AGENTS.md says small utilities are
LazyRAD by default and lists the exceptions: editors, custom painters, heavy
data. The Playground needs a code editor, a tree with thousands of rows, a
Markdown/Blitz doc pane and a high-rate live log; LazyRAD's controls
(`ListView`, `Edit`, `ComboBox`, ...) have none of those. It starts from
`python tools/xui/new_app.py playground ...`.

**D3. One execution path: every action is a script.** The call form, the
"Peek" button and the publish form all *generate Rhai*, put it in the editor
(or a scratch cell) and run it through the runner. No hidden native call path
that can differ from what a user later writes by hand. The only native Messenger
code in the app is the listener (D5) and the registry/topic list reads, which
are read-only.

**D4. Scripts run in a child `rhai` process, not in the app.** The command
already exists (`/system/bin/rhai`, static musl), is already limited
(`max_operations`, string/array caps), can be killed (Stop), and a script that
blocks in `msg::run()` or a 5 s call cannot freeze the UI. The app starts it
with pipes the way the LazyRAD IDE starts a player, reads stdout/stderr, maps
error positions back to editor lines. Several runs can be live at once (a
server script and its client; a watcher and a poker). The child inherits the
`tool:` label, so it holds what the app holds (`devtool-packages-plan.md`, section 1). P0 checks that
`rhai` reports error line/column and how a prelude is injected (see section 4).

**D5. Listening is native and doorbell-driven, never polled.** `fabricmon`
documents that `messengerd`'s heap never frees a receive buffer, so polling the
broker once a second exhausts it. The listener uses `Subscribe` + `Bell`
(`topics.v1`, `bell.v1`): one `Ready` wakes the UI, which drains with
expired-deadline `NextEvent`s. It also keeps a hard per-second cap and a
"events dropped by the viewer" counter so a firehose cannot starve the window.
Payloads are decoded with the schema codec (`rhai-lazy` as a library; if
pulling the Rhai engine into `xui-app` costs too much, extract `schema` + `codec`
into a `msg-schema` crate: P0 measures build time and binary size).

**D6. Docs come from the schema, with the Markdown as a "see also".** The
schema carries full doc comments for interfaces, methods, structs and topics;
`docs/idl/*.md` only has signatures, topic permissions and field lists. The doc
pane renders the schema's text and opens `/docs/os/idl/<interface>.md` and
`/docs/os/messenger.md` in the Docs app on demand.

**D7. Labelled as a developer tool; the risks are stated, not hidden.** A
script run here has the user's full Messenger authority. That is the point of
the app and also its danger, so it behaves like a developer tool, not like a
toy:

* **Marked as one**, by `xui_app::devtool`: menu category `development`; the
  window title carries "(developer tool)"; a thin strip (dismissible with its "x",
  remembered per user and tool, restored by View > Show developer-tool notice; it
  hides the band only, the title and the Help page keep the warning) under
  the menu bar reads "Runs with your full authority, exactly like the Terminal.
  Read a script before you run it." The Help page repeats the table below.
* **Opt-in.** Not in the default desktop image: `LAZYOS_DEVTOOLS=1` ships the
  developer tools as a class, and the `full` software suite includes it. No
  autostart.
* **Never runs on its own.** Opening a file, pasting, dropping, loading a
  Gallery entry or importing from the clipboard only fills the editor. Run is
  always an explicit key or click. A buffer whose text did not come from the
  user's typing (clipboard, file, share) asks once, before its first Run: "Run
  a script you did not write here?"
* **Privileged changes still go through `elevd`.** The trusted prompt names the
  requester ("Messenger Playground", a `tool:` label, not "Terminal") and an
  administrator approves; the Playground adds no shortcut.
* **Visible afterwards.** `PLAYGROUND:RUN` markers carry the run id, status and
  a hash of the script text, never the text, arguments or replies.
* **Not a sandbox, and never described as one.** The app does not claim a
  script from the internet is safe to try. It is the same trust decision as
  pasting into the Terminal.

| What a script can do | Consequence | What the app does about it |
|---|---|---|
| Stop or restart services, shut down (`init`) | Lost unsaved work, a broken session | Methods whose doc says so carry a warning chip in the doc pane and in `Call form`; `Call` of one asks to confirm. |
| Change or delete the user's own settings (`user/<uid>/**` in `confd`) | A broken terminal, theme or layout | `sys/**` and `/conf` are refused by the system, not by the app. The refusal text is shown. |
| Read the clipboard | Sees what the user last copied, perhaps a password | Clipboard methods are labelled "reads what you copied". Scripts are never run unreviewed (above). |
| Call credential interfaces (`keyd`, `accounts`) | Nothing: they are on the developer-tool deny list | The kernel refuses the call; the refusal text is shown and says to use the Terminal. |
| Launch apps (`mimed.Open`), post toasts | Look-alike notifications, surprise windows | A script's toast is owned by the Playground (LazyShell identifies a sender by its label, `devtool-packages-plan.md` 10.2 row 13), so a toast says who sent it; it is never "Terminal". The `elevd` prompt names the `tool:` label too. |
| Publish on user-level topics other apps trust | Spoofed events (`session/<s>/**` for the user's own session) | System topics are refused by the broker's ACL. The Publish form shows the topic's declared owner. |
| Open a network connection | Nothing: the socket service, name lookups, ping, mounts and a raw socket of the tool's own are all denied unless the manifest declares `network` | It does not. |
| Flood the fabric, exhaust `messengerd` | A slow or stalled desktop | `rhai`'s operation limit, Stop per run, the listener's rate cap (D5), and a visible per-run message counter. |
| Run a hostile script someone pasted | Everything above, at once | The review step, the strip, and no auto-run. |

## 3. The window

Two windows of one process (the user found one window too crowded: the topic tool is
its own window). The **main window** holds the Explorer, the doc pane, the editor and
the Output in two columns; the **Topic monitor**, "Messenger Topics (developer
tool)", holds everything about listening.

```
Main window "Messenger Playground (developer tool)"
+--------------------------------------------------------------------------------+
| File  Edit  Run  View  Help                                                    |
| [strip: Runs with your full authority ...                                  [x]] |
+---------------------+----------------------------------------------------------+
| [search........][R] | [Insert call][Call form][Serve skeleton][Connect]        |
| [Interfaces][Live]  | [Listen][Peek][Publish][Insert on_][Load example]        |
| [Topics][Gallery]   |  os.lazy.confd.v1.Get                                    |
|                     |  Get(path: String) -> (value: Option<Value>)             |
| v os.lazy.confd     |  Read the value at `path` ...                            |
|     Get             |  ARGUMENTS ...                                           |

|   > os.lazy.audio   | script.rhai     [Run F5]   | OUTPUT                      |
| ...                 |  1  let svc = msg::connect |  #{store_dir: ..}           |
|                     |  2  print(svc.info());     |  runs: #1 done              |
+---------------------+----------------------------+-----------------------------+
| Ready                          | runs live: 1 | topic monitor: 2 listening     |
+--------------------------------------------------------------------------------+

Topic monitor "Messenger Topics (developer tool)"  (View > Topic monitor, Ctrl+T)
+--------------------------------------------------------------------------------+
| Events  View                                                                   |
| [strip ...                                                                 [x]] |
| [filter events..............................]      [Pause] [Clear] [Pin]       |
| [time/tick][system/stats/m..]                                                  |
| time   topic      from           #   value                                    |
| 1.0s   time/tick  os.lazy.timed  2   #{ unix: 1760000001 }                     |
| [Copy as Rhai] [Save] [Stop listening]   Buffered/64 q0 d4 m4 drop0 ... pin1   |

|   from os.lazy.timed / sequence 2 / payload Tick / Tick { unix: ... }          |
| PUBLISH  [topic.........................................................]      |
|          [value....................] [ ] retained  [Publish] [Listen]           |
| Listening to time/tick                                  | listening: 1         |
+--------------------------------------------------------------------------------+
```

How the two windows relate: **one process, two `App`s** (`Ui::open_window`, the way Files
opens one window per folder), not a second process. The monitor owns the `Subscriber`, so
nothing is handed over on a wire and a Subscriber drop is the cleanup. The main window keeps
a `WindowHandle` and sends the monitor *requests* (`Listen <filter>`, fill the Publish form,
show); the monitor answers through the main window's `Proxy` (its Publish asks the main
window to run the one-line script so D3 still holds; how many subscriptions it holds; its
window closed). A second process would have needed a command topic, a registry check to avoid
duplicates and a second `Subscriber` hand-off for no gain. View > Topic monitor, the doc
pane's Listen and Publish buttons and the Topics tab's Listen open the monitor when it is
closed and send it their request; **Peek** stays a script run once whose output is in the
main window's Output. A client cannot raise its own window (`ActivateSurface` is the
shell's), so a request to an already open monitor is delivered and the status bar says to
find it in the taskbar. Closing the monitor drops it (every subscription ends, the
unsubscribe retried as before); closing the main window closes the monitor first and kills the
children.

* **Explorer** (left column, the whole height), four tabs.
  * *Interfaces*: every interface, collapsible to methods / structs / enums /
    topics, searchable by name, method, field or doc text. A `LIVE` badge when
    the registry currently serves it; a dim `not running` otherwise (many
    interfaces belong to optional services).
  * *Live*: the registry `List` as a table: name, interfaces (resolved from
    ids through the schema, or `0x...` for a hash with no schema entry, e.g. an
    app's own), owner uid and label, session, lease. Refreshed on a timer (it
    is a kernel read, safe to poll) and on demand. Selecting a row jumps to its
    interface.
  * *Topics*: declared topics (from the schema) merged with the broker's live
    list (`ListTopics`): pattern, payload type, QoS, retained, subscriber
    count, and the *Permissions* strings the docs print, so the user sees what
    a package would need to declare.
  * *Gallery*: the examples of section 6.
* **Doc pane** (right column, top; it is wide now that the topic tool left it): the selected node. For a method: doc, typed
  signature, the Rhai spellings (`msg::connect(...).get(...)` and
  `sys::confd::get(...)`), whether it is one-way, the objects it carries (and
  that a script cannot send them), and buttons. A struct shows its fields and
  where it is used; an enum its variants as the strings a script writes.
* **Topic monitor** (its own window): subscriptions as tabs; a decoded event list with
  time, topic, publisher (task slot resolved to the registry name that owns it, when one
  does), sequence, retained flag, and the selected event's metadata and value tree in a
  details list under it. Pause, clear, text filter, pin an event, "copy as Rhai map", "save
  to file". A strip shows the subscription's QoS, depth and the broker's `Stats` (queued,
  delivered, matched, drops), so *Latest* losing events is visible, not a surprise. Below
  the details a **Publish** form (topic, retained, a value typed as Rhai or a plain string;
  its Listen takes the topic as a filter). It has its own menu (Events, View), the
  developer-tool strip and a status bar, and Ctrl+W closes it, Ctrl+Q quits the tool.
* **Editor** (bottom middle): `xui-code-editor` with Rhai highlighting,
  diagnostics from the runner's errors, tabs for scratch scripts, `Ctrl+Enter`
  runs the selection, `F5` the whole buffer.
* **Output** (bottom right, beside the editor): one tab per run (id, state, elapsed), stdout and
  stderr, errors as links to the editor line, a Stop button per run. Closing the
  window stops every run it started.

### Actions the browser turns into script

| In the explorer | Insert / do |
|---|---|
| Method | `Insert call` appends a call with typed placeholders (`let r = sys::confd::get("path");`); `Call form` opens a generated form (String -> text box, enums -> combo of variant names, `Option` -> a toggle that sends `()`, `Array` -> add/remove rows, struct -> nested group, `Handle`/`Buffer`/`Channel` -> disabled with the reason); `Call` runs the generated line once and shows the reply tree in Output. One-way methods are labelled and use `invoke_oneway`. |
| Topic | `Listen` starts a native subscription (D5); `Insert on_...` writes the typed helper (`sys::confd::on_changed("sys/ui/#", \|e\| print(e.payload));`) or `msg::on`; `Peek` subscribes, takes the retained replay, unsubscribes (so the user can read `system/health/summary` without keeping a subscription open); `Publish` fills the form. |
| Live service row | `Connect` inserts `msg::connect(interface, name)` with the name that is really registered (covers `os.lazy.accountsd`-style names and Rhai-served `app.<id>.*` names). |
| Interface | `Serve skeleton` writes a `msg::serve(...)` with one handler per method, each returning a zero value of its reply type, ready to edit. |

### Guard rails

* Interfaces with secrets (`keyd`, `keyd.appsecret`, `accounts`, `elevd`)
  carry a banner. Generated snippets leave secret parameters empty; the app
  never stores or traces arguments, replies or run output for them. (As built
  there is no history file, so there is nothing to skip; the plan's "history
  skips runs that touched them" is not implemented and a script-text
  heuristic for it would be trivially bypassed. The authority is the
  Terminal's, so none of this adds power; it keeps the Playground from
  becoming a place passwords get pasted and kept.)
* A call that needs an administrator pops `elevd`'s trusted prompt, as from the
  Terminal. The doc pane says so when the method's doc mentions `elevd`.
* A refusal is shown as the service wrote it, with the errno name, plus a hint
  line: "denied by policy. Build an image with `LAZYOS_LABEL_TRACE=1` to see
  `LABEL:DENY`" (`docs/messenger.md` section 5).
* Publishing to a topic the user can subscribe to but not publish to shows the
  broker's refusal; the Playground does not try to bypass or pre-check ACLs.
* The risk chips and confirmations of D7 apply to `Call form` and `Call`; hand
  written scripts are the user's own and only get the D7 review step.

## 4. Architecture

```
xui-app/src/bin/playground.rs      launch::run(Channel::Playground, ...), Platform glue only
xui-app/crates/playground/         portable, host-tested, no LazyOS types
    catalog.rs      schema + live registry/topics join -> tree nodes, search index
    docs.rs         node -> doc blocks (schema text), Rhai spellings, sys:: alias rule
    snippet.rs      node -> Rhai text (call, serve skeleton, on_/subscribe, publish), placeholders
    form.rs         method/struct/topic payload -> form model <-> Rhai value text
    show.rs         Rhai/TLV value -> pretty tree text, "copy as Rhai"
    listener.rs     subscription model: Bell drain, rate cap, drop counters, ring of events
    runner.rs       child-process model: spawn, pipes, line mapping, Stop, run table
    gallery.rs      example manifest (title, tags, needs, expected output)
xui-app/packages/playground/       manifest (kind = "developer-tool"), icons, examples/*.rhai (D1)
tools/playground/                  run.py, test_judge.py (the guest harness)
```

* The crate splits UI from model on purpose: `catalog`, `snippet`, `form`,
  `show` and `listener` are pure functions over the schema and are tested on the
  host without QEMU. The UI layer is thin widgets over them.
* **Snippet correctness is a property test.** For every method of every
  interface in the table, the generated call compiles under the `rhai-lazy`
  engine and, run against the in-memory fabric the crate's own tests already
  use, encodes without a codec error. A new `.midl` that breaks the generator
  fails `cargo test`, not a user's click.
* **Runner prelude.** A small prepended module (`pg::show(v)` pretty-prints a
  value; `pg::sleep_ms`) is injected as text and the line offset is subtracted
  from error positions. If `rhai` supports file imports from a package
  directory P0 uses that instead.
* **Live tables are cheap.** Registry `List` is a kernel read; the topic list
  is read at most every 10 s (the `fabricmon` rule `TOPICS_EVERY`), never in a
  tight loop.
* **No new IDL.** The app is a Messenger client only. The optional toy
  interface for the examples (P4) is the one `.midl` this plan could add, and it
  follows the usual route (`midlc`, regenerate `libs/rhai-lazy` table and
  `api/`, `docs/idl`, CI `--check`).
* **Evidence markers** go through `xui_app::trace` on a new `Channel::Playground`
  (`tools/xui/new_app.py` writes the row): `PLAYGROUND:UP:PASS`,
  `PLAYGROUND:OPEN:<interface>`, `PLAYGROUND:RUN:<id>:START|EXIT:<status>`,
  `PLAYGROUND:LISTEN:<filter>`, `PLAYGROUND:EVENT:<topic>:<seq>`,
  `PLAYGROUND:CALL:<interface>.<method>:OK|ERR:<errno>`. Never arguments,
  payloads or replies. Probe rectangles (`UI:RECT`/`UI:WIDGET`) name the tree
  rows, buttons, editor and output tabs so sessions click by name.

Wiring, as AGENTS.md requires for every app, goes through the developer-tool
class (`devtool-packages-plan.md`, T4): the build switch `LAZYOS_DEVTOOLS=1`
(implies `LAZYOS_DESKTOP=1` and the `rhai` command), `run_demo.py --devtools`,
the GUI control (Simple tab: *Developer tools*; Advanced: the raw switch)
through `tools/lazygui/catalog.py` with tests in `test_catalog.py`, and the
`devtools` entry of `tools/suites.toml` (`full` includes it; `python
tools/test_suites.py` fails otherwise). The Playground adds its own package
(`xui-app/packages/playground/`, listed in `tools/xui/core_packages.py`), whose
manifest has no `interfaces` or `topics` (the kind is default-allow). There is
no "not a package" exception to record in `AGENTS.md`. Verification starts from
`run_demo.py --devtools`, not hand-set variables.

### Testing

* Host: `cargo test --manifest-path xui-app/Cargo.toml -p xui-playground`
  (catalog, search, docs, snippets, forms, `show`, listener accounting, runner
  line mapping against a fake child), plus seeded fuzz of the form <-> Rhai
  text round trip and of the event decoder with arbitrary payload bytes (the
  broker's payload is "opaque"; decoding must never panic).
* Offscreen window snapshots in `xui-app/target/snapshots/playground-*.png`: Read
  them.

## 7. Risks and open questions

1. **The authority is close to the Terminal's, on purpose.** A default-allow
   label is a new idea in a system whose point is that apps hold nothing. The
   guards are in `devtool-packages-plan.md` section 7 (a reviewed deny list with
   a test, a CI check that fails on an unclassified new interface) and D7
   (honest labelling, opt-in, never auto-run, `elevd` still the gate). If that
   proves too much for a "playground", the way out is permission classes
   (`permission-classes-plan.md`, shelved) or a derived label, not a quieter
   banner.
2. **Broker heap.** The `fabricmon` note about `messengerd` never freeing
   receive buffers is the reason for D5. P0 checks whether it still holds and
   whether a long listen (hours, `time/tick` at 1 Hz) is safe; if not, a
   listen session gets a time/count budget and says so.
3. **`msg::run` blocks the child, not the UI**, but a run that never ends is a
   leaked process if the window crashes. The runner records child pids and the
   window kills them on exit; `init`'s session teardown is the backstop.
4. **Name collisions.** A Rhai-served name (`demo.pirate`) is taken until its
   run ends; the Live tab shows the owner so the user sees why a second serve
   fails.
5. **Publisher identity.** The event's `publisher` is a task slot; slots are
   reused. The UI resolves it against the registry at receive time and shows
   `?` when it cannot, never a stale name.
6. **Blitz cost.** If rendering schema text through Blitz is heavy for a
   thousand-node tree, the doc pane draws plain styled text and uses Blitz only
   for the Markdown "see also" pages.
7. **Per-field docs.** The schema has struct and method docs but no per-field
   docs; `docs/idl/*.md` lists fields without them either. The pane shows
   what exists and does not invent text; adding field docs to `midlc`'s table is
   a small follow-up that every other consumer (`msg::describe`, the docs) gets
   for free.
8. **Pre-PR review** (AGENTS.md): each phase's PR gets a review from a separate
   agent covering the project conventions above (no ad hoc prints, `libs/fhs`
   paths, files under 500 lines, launcher/GUI wiring, visual verification) and,
   for D1, the developer-tool deny list and D7 (strip, no auto-run, review step).

The window, the runner glue and the guest harness exist (P1 to P3 and the P5
pieces below, D1/D3/D4/D5/D7). Source: `xui-app/src/bin/playground.rs` and
`playground/` (`app`, `selection`, `formctl`, `callform`, `docview`, `explorer`,

`test_judge.py` (17 tests: a good log per session passes, every defect fails),

**What the window is.** Menu bar, the `devtool` strip, an Explorer (Interfaces

**The Topic monitor window** (`bin/playground/topicswin.rs`, `topicsui.rs`, `topics.rs`,
`publish.rs`, `tmsg.rs` for the window; `topicshost.rs` for the main window's side). One
process, two apps: `TopicsTool` is an `App` with its own `TMsg`, opened by

sends `TMsg::Request(Listen | FillPublish | Show)` and, after each registry read (2 s), a

monitor sends `Msg::PublishRequest` (the main window runs the one-line script: one
execution path), `Msg::TopicsStatus(n)`, `Msg::TopicsGone` and `Msg::NoticeChanged`. The pure
parts are tested on the host: `topicshost::plan` and `status_text`, `topics::details_rows`
and `stats_text`, `publish::publish_script`, the shortcuts. `Drop for TopicsTool` ends the
subscriptions and prints `PLAYGROUND:TOPICS:QUIT:PASS`; `TOPICS:UP:PASS` is printed with the

an "x" (probe `devtool:strip_dismiss`); the choice is the marker file

`PLAYGROUND:NOTICE:HIDDEN`, `NOTICE:SHOWN` and, at start with the choice stored,

`notice` before `notice_stored`).

**Differences from the plan.**

* A run's script goes to `rhai -` on standard input (no temp file to leave
  behind); the prelude is prepended and errors map back through `run_map`.
  Examples are the crate's embedded copies, not read from `resources/examples`.
* Peek and Publish are generated scripts (D3), run once in an Output tab.
* Doc-pane buttons sit in two fixed rows above the pane; the Call form's Call,
  Insert and Close sit under it. Stop is one button for the selected (else
  newest live) run, not one per tab. One editor buffer, no scratch tabs, no
  history file. The selected event's value tree is shown in the Topic monitor's
  details list under the events, not in the doc pane.
* Listen: the bell is looked at by a 100 ms
  timer that reads only the local bell channels (`consume_ready`, never the
  broker) and exists only while something is listened to; a full drain batch is
  continued by a 20 ms one-shot. The window's wait does not name the bells, and
  the backend was not edited. `Stats` is read on a tab change or Pause, never on
  a timer. The topics list is read from the broker only when the Topics tab
  opens (at most every 10 s) or Refresh is pressed, never on a timer. A
  subscription is closed after 20 000 events (the broker keeps a buffer per
  call); that budget is a guess, the long-listen risk of section 7 is not measured.
* A call of a method that stops services (`init`, `lifecycle`, `logind` lists in
  `docs::risks`) asks on a confirm card; a paste, file or share asks once before
  its first Run (`devtool::ReviewGate`, the only gate: the portable crate has
  no copy of it). An arrival is detected at the source and from the text:
  the editor's clipboard is wrapped (`bin/playground/paste.rs`), so Ctrl+V and
  Edit > Paste mark the next edit as a paste however short it is; and
  `xui_playground::arrival` judges every edit by what it *inserted* (common
  prefix and suffix of the old and new text, not the buffer's net growth), so
  a select-all paste of a shorter script, a paste over a selection and a drop
  all count. A key inserts one character or only white space (Enter, Tab),
  so two or more visible characters in one edit is an arrival. Undo and Redo
  to a text the gate had vouched for (typed, confirmed or shipped, kept in
  `Known`) are not arrivals: undoing in a confirmed script stays confirmed and
  undoing a paste gives the user's own text back; Redo of an unconfirmed
  paste asks again.
* Runs: at most 8 are live (`runner::MAX_LIVE`; the 9th is refused with a
  note, no child started). Each run has its own bounded output queue (256
  events of at most 4096 characters; a full queue blocks the reader threads
  and so the child's `write`), the window is rung at most once until it has
  looked (`Wake`), and it takes at most 512 events per look, round-robin
  over the runs. Each `rhai` child asks the kernel for `SIGKILL` when the
  Playground process exits (`PR_SET_PDEATHSIG` between `fork` and `exec`,
  kept by `execve`); `init.Stop` of the app kills only the app's own task
  (`Quit`/`SIGTERM`, `SIGKILL` after 3 s), and only a logout sweeps a whole
  session, so without that a child outlived a killed Playground until
  logout. Unverified in a guest with the Playground (the mechanism is
  exercised by the `threadreap` ABI fixture and the kernel's `pdeathsig`
  tests).
* Probe names: `tree_row:<n>`, `gallery_row:<n>`, `topics_row:<n>`,
  `live_row:<n>`, `events_row:<n>` (the first six rows of each), `search`,
  `editor`, `run_button`, `stop_button`, `btn:<action>`, `form_call`,
  `pause_button`, `pub_topic`, `pub_payload`, `pub_listen`, `pub_go`, ... A tab
  page's children report coordinates relative to the page, so the probe adds
  the tab strip (32 dip) to the tabs' top-left.

## As built: layout and scrolling

**The main window's layout** (`bin/playground/ui.rs`, `panes.rs`, `panesapp.rs`, `menus.rs`).
xui-core (the pinned `va1erian/xui` revision) has a `Split`: two panes and a draggable divider
(`xui_core::widget::Split`, `arrange::split`), used here for both dividers. Stretch policy: the
Explorer | right column split is a fixed design width (default 340, 240 to 640, the right column at
least 420), so a bigger window gives all its extra width to the right column; the doc pane | editor
row split is a stacked `Split` whose position the app sets from the doc pane's *share* of the column
(default 0.55, 0.2 to 0.85, each pane at least 150 and 130 design pixels) at every `Resize`, so the
doc pane and the editor/Output both grow in proportion. Dragging a divider updates the share. The
choice (Explorer width, share, bottom row shown) is remembered per user in
`$HOME/.apps/os.lazy.playground/layout` (three `key=value` lines; optional, a bad or missing file is
the defaults, a failed write is dropped), written when a drag settles (next 2 s tick) and at quit.
There is no double-click reset (`Split` has none).

**The bottom row is togglable**: View > "Editor and output" (a check item), Ctrl+J, and a
Hide/Show editor button at the right end of the Call form row. Hidden, the row's panel is hidden
(nothing in it takes input or focus; the focus moves to the page being read) and the doc pane takes
the whole column; the divider stays at the bottom edge and pulling it up shows the row again.
Running a script (including Peek, a Call form's Call), Insert call, Serve skeleton, Connect, Insert
on_, Call form's Insert, Load example, Open, New and double-clicking an error line in Output show it
again (`reveal_bottom`, applied at the end of the update). The toggle runs nothing and stops nothing:
runs and their Output go on while hidden, and the status bar keeps "runs live: n". Markers
`PLAYGROUND:LAYOUT:BOTTOM:SHOWN|HIDDEN`, `LAYOUT:SAVED:<explorer>:<share>`,
`LAYOUT:LOADED:<explorer>:<share>:shown|hidden`; probe names `toggle_bottom`, `split_main`,
`split_doc` (the divider's rectangle), `bottom_row`, `doc_bar_top` (the doc pane's scroll thumb at the top), and every rectangle is now window-absolute
(`LazyOSBackend::window_bounds`), since controls sit inside the dividers' panes. Sessions `layout`
and `layout_stored` (run them last; they leave a dragged layout stored on the volume).

**Why the doc pane scrolled unlike the Explorer** (found with `tools/playground/scroll_run.py`,
`scroll_tests.rs`, `layout_tests.rs`):

* *The wheel was lost over text.* `xui-core` has no event bubbling (`WidgetHost::deliver` says so)
  and both its backends deliver the wheel to the deepest node under the pointer. A scroll view's
  content (labels, wrapped text, links) are its children, none of them reads the wheel, so the page
  scrolled only when the pointer happened to be on bare view. The tree and the lists are one node
  that reads its own wheel. Fix in the LazyOS backend (`backend/wheel.rs`): a roll over a node that
  passes the wheel (labels, buttons, containers, a scroll view's own bar, ...) goes to the nearest
  `ScrollView` above it; list, tree, editor and custom nodes keep it, a capture keeps it. The
  compositor also hands a quick roll over as one event carrying its notch count, and `xui`'s scroll
  view moves one step per event whatever the count (3 notches scrolled 1 step, found in the guest),
  so the backend delivers one `MouseWheel` per notch (at most 16 per roll).
* *A thumb drag showed nothing until release.* Each pointer move made the scroll view re-measure
  and re-place its whole content, and a `FlowText` re-shapes every word on each measure: 35 to 60 ms
  a step on the big interface pages (host release build, `survey`), more in the guest. The backend
  reads all queued input, then presents once, so with moves arriving faster than a step the queue
  never drained until the button came up: nothing moved, then everything jumped. Fixes: the backend
  merges the pointer moves of one input batch into the last one (wheel rolls are never merged: widgets scroll one step per event)
  (`backend/coalesce.rs`, order with presses kept), and the doc pane's page is one painted
  widget (`docbody.rs`) that lays out once per width and paints only the damaged part, so a step
  moves one node (0.03 to 0.3 ms per step on the same pages, a 200 fold). The page keeps the same
  text; its blocks are tighter than the labels'.

Host tests: `cargo test --manifest-path xui-app/Cargo.toml --bin xui-playground` (layout at four
window sizes, hidden row, divider drags, scroll cost and live drag, links) and `--lib backend::`
