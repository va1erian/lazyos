# Plan: install LazyOS beside Linux, behind the existing GRUB

> **Status: draft, revision 2 (2026-10-10). Decision 1 (the installer runs
> from Linux) is confirmed. I0's survey additions are in
> `tools/boot/survey_linux_box.sh`; nothing else is built.**
> Target: the Kaby Lake box ([`kabylake-box-plan.md`](kabylake-box-plan.md):
> a 512 GB M.2 SATA SSD behind an AHCI controller, UEFI, a Linux install
> already on it), and any UEFI PC set up the same way. Builds on
> [`usb-stick.md`](usb-stick.md) (what the stick is made of),
> [`ahci-plan.md`](ahci-plan.md) (the SATA driver),
> [`architecture/block-devices.md`](architecture/block-devices.md) (root and
> home selection by `lazyos.cfg`) and sits beside
> [`nvme-install-plan.md`](nvme-install-plan.md), which takes the whole disk
> and owns its own layout and GPT work, and [`update-plan.md`](update-plan.md).

## I0 results (the Kaby Lake box, survey of 2026-10-10)

From [`compat/kabylake/grub-survey/`](compat/kabylake/grub-survey) (redacted
with `tools/boot/redact_survey.py`):

- **UEFI, Secure Boot off** (`mokutil`: disabled, Setup Mode). GRUB 2.14
  (Ubuntu), shim chain `\EFI\ubuntu\shimx64.efi`.
- **Disk:** one 512 GB SATA SSD, GPT, 512 B sectors, two partitions today:
  `sda1` 300 MiB FAT32 ESP (292 MiB free) and `sda2` ext4 `/` (476.6 GiB, with
  `/boot` on it). **The two LazyOS partitions do not exist yet**: the Linux
  side must shrink `sda2` first.
- **`/boot/grub` is on ext4**, reached through the ESP stub
  `EFI/ubuntu/grub.cfg` (`search.fs_uuid` then `configfile`): confirms
  decision 1, LazyOS cannot write GRUB's config.
- **`custom.cfg` is sourced** by the generated `grub.cfg` (lines 400-403), so
  the fallback in step 7 works here; `/etc/grub.d` has `40_custom`,
  `41_custom` and `30_os-prober` (our `40_lazyos` coexists).
- **The menu is hidden** (`GRUB_TIMEOUT_STYLE=hidden`, `GRUB_TIMEOUT=0`): the
  entry will not show without Shift/Esc at power-on. The installer does not
  change `/etc/default/grub`; it prints this, and the trial boot uses
  `grub-reboot`, which works on a hidden menu (`next_entry` is read at
  `grub.cfg` line 31).
- **ESP space is ample** (292 MiB free for a kernel and a 1 MiB ramdisk).
- `sgdisk` is not installed by default; the installer reads GPT itself and
  must not require it.

## Goal and scope

A Linux install (done by the person, with its own tools) has already
produced, on the SATA SSD: a UEFI ESP, GRUB installed and working, and two
empty partitions meant for LazyOS, one for the system and one for `/home`,
both nominally ext2. One command then makes LazyOS a menu entry of that GRUB
that boots the machine from those two partitions, with no stick plugged in.
Linux keeps booting exactly as before.

**Out of scope, by decision:** creating or resizing partitions, installing
or repairing GRUB itself, Secure Boot signing (it stays off, as for the
stick), BIOS/CSM GRUB (v1 is UEFI only, see decision 6), dual-boot with
Windows, disk encryption, swap, A/B updates (the layout has no room for them;
see "Updates").

## Decisions

1. **The installer runs on Linux, not inside LazyOS.** Everything it must
   touch that LazyOS cannot is Linux's job: the GRUB configuration lives on
   the distro's `/boot` (usually ext4, which `libs/ext2fs` refuses) and is
   regenerated by `update-grub`/`grub2-mkconfig`; the ESP is FAT32, which the
   kernel cannot read (#248) and nothing in user space writes; and a native
   installer needs `CAP_BLOCK_RAW`, the first user-space authority to write a
   whole disk (nvme-install-plan risk 6). Running from the Linux that is
   already there needs none of that and exercises the real GRUB. A native
   `lazyinstall` (N3 of the NVMe plan) is a later front end over the same core.
2. **The stick is the payload.** "Copies itself" is literal: the stick's FAT
   partition already holds the loader (`efi/boot/bootx64.efi`), the kernel
   (`kernel-x86_64`) and `ramdisk`, a whole-disk image whose entry 2 is the
   OS volume (`usb-stick.md`, "Image layout"). The installer reads those
   files from the mounted stick; there is no second build product to keep in
   step, and the bytes installed are the bytes CI booted from a stick.
3. **GRUB chainloads the `bootloader` UEFI stage; it does not load the kernel.**
   The kernel is a `bootloader`-crate kernel (`BootInfo`), not Multiboot, and
   the stage already works on this firmware. One entry, static, found by
   filesystem UUID, so it never changes when LazyOS does:

   ```
   menuentry "LazyOS" --class lazyos {
       insmod part_gpt
       insmod fat
       insmod chain
       search --no-floppy --fs-uuid --set=root <ESP FAT UUID>
       chainloader /EFI/lazyos/BOOTX64.EFI
   }
   ```

   Under `chainloader` the image's device handle is the ESP, which is where
   the loader looks for its files. A Multiboot2 entry in the kernel (GRUB
   loads kernel and module from ext2, no ESP files at all) is the clean
   long-term shape and a separate plan; see "Later".
4. **The boot configuration travels as a tiny ramdisk, so the kernel needs no
   FAT32.** The ESP's FAT32 is unreadable to the kernel, but the loader
   already hands over a `ramdisk`, and a ramdisk whose boot volume carries
   `lazyos.cfg` wins root selection while `root=UUID=` is "found by UUID, on
   any device" (block-devices.md). So the installer writes a 1 MiB
   MBR + FAT12 image holding only `lazyos.cfg`
   (`root=UUID=<system>`, `home=UUID=<home>`, `display.*`/`limit.*` lines) as
   `\EFI\lazyos\ramdisk`. That ramdisk-config-plus-disk-root combination is
   not exercised today (the stick's root is *in* the ramdisk); it gets a
   kernel test in K3.
5. **The OS volumes are made by the code that makes every other OS volume.**
   Linux's `mke2fs` and `cp` would put features and htree directories on the
   volume that the LazyOS driver never writes into (it accepts `dir_index`,
   `ext_attr` and `resize_inode` as compat features but only knows
   `filetype`, `sparse_super`, `large_file`). So the installer ships one
   static musl binary, `lazyos-install`, built from `libs/ext2fs` and the
   `build_support/os_*.rs` logic (`format`, populate, and the in-place update
   driven by `/system/.image-manifest`), and applies it to the partition
   device with the volume unmounted. The result has the same layout, modes,
   manifest and checker verdict as `target/lazyos.img`'s OS volume.
6. **UEFI only in v1.** The BIOS loader boots from an MBR with its stages at
   fixed LBAs; there is no sane GRUB chainload of that onto a disk Linux
   owns. A BIOS-GRUB box is refused with a message, not half-supported.
7. **Never touch what is not ours.** The installer writes exactly: the system
   partition, the home partition (first install only), `\EFI\lazyos\` on the
   ESP, one GRUB snippet. Nothing else, and it undoes the last two with
   `uninstall`. The partitions are named by the user (`--system /dev/sda5
   --home /dev/sda6`) or found by GPT partition name `lazyos-system` and
   `lazyos-home`; it refuses a mounted partition, the running root, the
   stick's own disk, and anything that is not a partition of the same disk as
   the ESP, and makes the user type the device name back before formatting.

## The installed layout

Four partitions Linux made (existing names vary; sizes are minimums):

| Partition | Format | Owner | LazyOS use |
|---|---|---|---|
| ESP, FAT32, existing | the distro's | Linux + GRUB | gains `\EFI\lazyos\{BOOTX64.EFI, kernel-x86_64, ramdisk}` (about the kernel size plus 1 MiB; installer checks free space) |
| Linux root (`/boot/grub` here, usually) | ext4 | Linux | gains `/etc/grub.d/40_lazyos` and a regenerated `grub.cfg` |
| `lazyos-system` | ext2 | LazyOS | `/`: programs, `/conf`, `/apps`, `/logs`, `/docs/os` (4 GiB recommended, 1 GiB minimum for the desktop profile) |
| `lazyos-home` | ext2 | LazyOS | `/home` |

Boot chain:

```
 firmware ─► GRUB (the distro's, on the ESP) ─► menu: Linux ... | LazyOS
   LazyOS ─► chainloader \EFI\lazyos\BOOTX64.EFI  (bootloader UEFI stage)
          ─► loads kernel-x86_64 and ramdisk (config only) from the ESP
 kernel: PCI ─► ahci0 ─► GPT: ahci0p1..p<n> (K2)
         ─► ram0p1 carries lazyos.cfg ─► / = ext2 <system UUID> (rw)
         ─► /boot = ram0p1 (ro), /home = ext2 <home UUID> ─► init ─► desktop
```

A stick plugged in while booting the installed entry changes nothing: the
config names UUIDs, not the stick's `lazyhome` label. The reverse also holds:
the stick's ramdisk wins on a stick boot (block-devices.md), so both can be
present. The stick build should move to `home=UUID=` as the NVMe plan already
proposes.

## The installer

One binary, `lazyos-install` (`tools/install/`, static musl, built by
`tools/install/build.py` like `tools/nettls/build.py`), run as root:

```
sudo /mnt/stick/install/lazyos-install            # interactive; shows everything first
sudo ./lazyos-install --system /dev/sda5 --home /dev/sda6 --esp /boot/efi --yes
./lazyos-install --image disk.img ...             # test mode: files, no root (I3)
./lazyos-install update | uninstall | status
```

`install`, in order, stopping at the first failed check (nothing is written
before step 6):

1. **Probe.** UEFI boot (`/sys/firmware/efi`), GRUB present (`grub-install` or
   `grub2-install`, `/boot/grub*/grub.cfg`), the ESP (the mounted
   `/boot/efi`, or the partition of type `C12A7328-…`), GPT on the disk.
   Report distro, GRUB version, `/boot` filesystem, Secure Boot state
   (`mokutil --sb-state`; warn, do not fail).
2. **Validate partitions** (decision 7), sizes, that the system partition
   holds at least the payload's ext2 volume, and ESP free space.
3. **Plan.** Print what will be written where, the new fs UUIDs, the
   `lazyos.cfg` and the GRUB entry. `--dry-run` stops here.
4. **Confirm.** Type the system partition's device name back.
5. **Format and populate** system (`ext2fs::format`, every file from the
   ramdisk's OS volume, the manifest, modes and owners, the layout
   directories); format home (`ext2fs::format`, same features) on a first
   install, and optionally copy the stick's `lazyhome` into it.
6. **Write the ESP files** to a temporary name in `EFI/lazyos/`, `fsync`, then
   rename into place: the loader, the kernel, the generated config ramdisk.
7. **Register with GRUB.** Write `/etc/grub.d/40_lazyos` (mode 755; the
   entry above with the ESP's UUID), run the distro's regenerate command
   (`update-grub`, `grub2-mkconfig -o <path>`, found not assumed), and read the
   generated `grub.cfg` back for the entry. When there is no `/etc/grub.d`
   (a distro that does not use `grub-mkconfig`), append the entry to
   `$prefix/custom.cfg` (sourced by upstream's `00_header`; checked in I0) and
   say so.
8. **Verify.** Re-open both volumes with the independent ext2 checker
   (`libs/ext2fs/src/check.rs`) and compare SHA-256 of the three ESP files
   against the stick.
9. **Offer a trial boot**: `grub-reboot "LazyOS"` sets GRUB's `next_entry`
   once, so a LazyOS that does not come up costs one power cycle and the next
   boot is Linux again.

`update` re-runs step 5 in place from the manifest (the same replace/delete
rules as a rebuild: `/conf`, `/apps`, `/logs`, `/home` and anything the user
made survive), then step 6 and 8. `uninstall` removes `\EFI\lazyos\`, the
snippet and regenerates `grub.cfg`; the partitions are left for the user.

## Updates and recovery

- **v1 update is in place and offline:** boot Linux (or the stick's Linux-side
  tooling), run `lazyos-install update`. Power loss mid-update can leave the
  kernel and `/system` from different releases; v1 accepts that, keeps the
  Linux entry as the way back, and `update` writes the new kernel last. A real
  A/B scheme needs two more partitions and the slot-aware loader of
  [`update-plan.md`](update-plan.md); the layout leaves that open (the Linux
  install can add partitions later without touching home).
- **Unclean power-off:** same story as the stick and NVMe plans: ext2 without
  a journal, flusher bounds the loss to ~5 s, the next Linux boot can
  `e2fsck` the two partitions (they are plain ext2 with a feature set stock
  `e2fsck` understands). `LAZYOS_JOURNAL=1` volumes are *not* offered here: a
  journal feature Linux's ext2 driver would not replay is a trap for the
  person fixing it from Linux.
- **GRUB gone or broken:** the stick still boots LazyOS on its own, and the
  Linux install is the recovery environment for GRUB, which is where that
  repair already belongs.

## Risks and open questions

1. **Where does the installer run?** This plan chooses Linux (decision 1)
   because every blocker is a Linux-side file. If the intent is "boot the
   stick, press install, never see Linux", the native `lazyinstall` of the
   NVMe plan is needed *and* a FAT32 writer in user space, an ext4-capable
   write path to GRUB's config or a manual step, and `CAP_BLOCK_RAW`. Worth
   deciding before I2.
2. **GPT is a hard dependency.** A UEFI Linux install is GPT; until K2 lands
   the kernel sees no partition on the box's disk. If K2 slips, the fallback
   is a hybrid or MBR disk layout, which the Linux installer would have to be
   told to make (unusual on UEFI).
3. **Fixed loader file names.** If the `bootloader` UEFI stage only reads the
   volume root, `kernel-x86_64` and `ramdisk` sit at the ESP root, visible to
   every EFI tool and to the distro's own `\EFI\BOOT` fallback if a name ever
   clashes. K4 prefers a patch to read `\EFI\lazyos\`.
4. **A small ESP.** Some installers make a 100 MiB ESP already holding two
   distros' shims. The installer checks free space before writing and refuses
   rather than evicting anything.
5. **`chainloader` and the device handle.** The loader assumes its image's
   device handle is the volume with its files. That is how GRUB's
   `chainloader` works for an EFI binary on a firmware-visible partition, but
   it is the one assumption nothing in this repo has run; I3's real-GRUB run
   is the proof, I4 the confirmation. If it fails, the entry can use
   `chainloader (hd0,gptN)/EFI/lazyos/BOOTX64.EFI` with an explicit device, or
   the Multiboot2 route below.
6. **Secure Boot** must be off (the kernel and the loader are unsigned); a
   shim-only chain refuses them. The installer warns; signing is a separate
   S9 item.
7. **`custom.cfg` is a convention, not a guarantee.** Upstream's `00_header`
   sources it; a distro that generates `grub.cfg` another way (a static file,
   a BLS-only setup) ignores the snippet. The installer says which path it
   used and prints the entry to add by hand when it cannot register one.
8. **The static binary and `build_support`.** `build_support` is a
   host-build crate; sharing it with a shipped binary means extracting the OS
   volume logic into a library the build and the installer both depend on.
   That is a refactor the build's host tests (`cargo test -p
   build-support-tests`) must stay green through, and it is most of I2's cost.
9. **Time and clock.** The installed machine's RTC is whatever Linux left
   (localtime vs UTC); LazyOS's clock handling is the stick's, unchanged.

## Later

- **Multiboot2 entry for the kernel.** GRUB would load `kernel-x86_64` and a
  config module from the system partition's ext2 directly: no ESP files, no
  FAT32 problem, no loader file names, one `menuentry` that never mentions
  the ESP. The cost is a small entry stub that turns Multiboot2's memory map,
  framebuffer and RSDP tags into `BootInfo`; it also unlocks BIOS GRUB.
- **A/B slots** with the update plan's loader and `lazyboot` control block,
  once the Linux install can be asked for two more partitions.
- **Native `lazyinstall`** (nvme-install-plan N3) over the same core, for a
  box with no Linux, and the graphical installer N5.
