# WebKit, webd and the browser

Companion to [`AGENTS.md`](../../AGENTS.md); Javascriptcore, the webkit dependency bundle and port, lazyweb+ and webd.

## JavaScriptCore (`LAZYOS_JSC=1`: `jsc`, `cxxproof`)

`tools/jsc/build.py` builds WebKit's `JSCOnly` port (WebKitGTK 2.54.1, the
C-loop interpreter, ICU 74.2 with its data inside) and a C++ toolchain proof
as static musl programs with zig, **inside Docker** (`tools/jsc/Dockerfile`,
Debian 12 with cmake, ninja, ruby, perl; `--no-docker` on a Linux host runs
the same steps). `LAZYOS_JSC=1` (`run_demo.py --jsc`, which implies
`--big-app`) puts `jsc` and `cxxproof` in `/system/bin`; `python
tools/jsc/run.py` builds the image, boots it with 2 GiB and judges the
`JSC:W1:*`, `JSC:UP:PASS` and `JSC:RUN:PASS:<name>` markers
(`tools/jsc/test_judge.py` is the judge's self-test). Plan, numbers and the
problems found: [`docs/webkit-port-plan.md`](../webkit-port-plan.md),
details in `tools/jsc/README.md`.

```bash
python tools/jsc/build.py            # Docker: ICU, cxxproof, jsc -> target/jsc/bin
python tools/jsc/run.py --accel none # boot and judge (add --stage w1 for the C++/ICU proof alone)
python tools/jsc/test_judge.py
```

## WebKit dependency bundle (`LAZYOS_WEBKIT_DEPS=1`: `depsproof`)

`tools/webkit/deps.py` builds every library WebCore and the WebKit layer need
at WebKitGTK 2.54.1 (zlib, brotli, libpng, libjpeg-turbo, libwebp, FreeType,
expat, HarfBuzz, Fontconfig, libxml2, SQLite, libpsl, OpenSSL, nghttp2, curl,
ICU, and Skia from inside the WebKit tarball) as static musl archives with zig,
in the `jsc` build's Docker container, into one prefix, with
`target/webkit/deps.json`, plus `depsproof`, a C++ program that uses each
library. `LAZYOS_WEBKIT_DEPS=1` (`run_demo.py --webkit-deps`, which implies
networking and `--big-app`) puts it in `/system/bin`; `python
tools/webkit/run.py` builds a console image with the TLS harness's test CA,
fetches a page from the host's TLS server and judges `WEBKIT:W3:PASS:<lib>`
and the pixels against the same program's run on the build host
(`tools/webkit/test_judge.py` is the judge's self-test). Plan, library table and
decisions: [`docs/webkit-port-plan.md`](../webkit-port-plan.md) §5 W3,
details in `tools/webkit/README.md`.

```bash
python tools/webkit/deps.py            # Docker: the libraries, Skia, depsproof -> target/webkit
python tools/webkit/run.py --accel auto # boot and judge
python tools/webkit/test_judge.py
```

ICU's data is cut before it is compiled in (30.8 MB to 9.9 MB, policy and proof in `tools/jsc/icudata.py` and
`icudata_check.c`; a locale outside its list formats like English), and the WebKit programs are built without unwind
tables, with lld `--icf=safe` and `-Os` for cold targets: `webkit/README.md`, "Size of the programs".

## The WebKit port (`LAZYOS_WEBKIT_PORT=1`: `WebProcess`, `NetworkProcess`, `webkit-smoke`)

`webkit/` holds the LazyOS port of WebKit2 (W4): `port/tree` (the
`OptionsLazyOS.cmake` and `PlatformLazyOS.cmake` files and the few LazyOS
sources, laid over the pinned WebKitGTK 2.54.1 tarball), `patches/`,
`port/upstream.txt` (files of WebKit's git the tarball lacks, fetched by blob
digest), `port/smoke` (the headless UI process, WebKit's C API) and
`port/fonts.conf.in`. `python tools/webkit/port.py` (after `deps.py`, which now
also builds libwpe and the EGL/GLESv2 stand-ins) builds the three programs in
the `jsc` Docker container; a rebuild is incremental. `LAZYOS_WEBKIT_PORT=1`
(`run_demo.py --webkit-port`, which implies networking and `--big-app`; a GUI
checkbox) embeds them (as `/system/bin/webprocess`, `networkprocess` and
`webkit-smoke`, with `fonts.conf` and the Liberation fonts); `python tools/webkit/port_run.py` builds a console image,
types `webkit-smoke` and judges `WEBKIT:W4:*` (`tools/webkit/test_port_judge.py`
is the judge's self-test). **WTF, JSC and bmalloc must stay the JSCOnly
configuration**: the port's platform macro is `PLATFORM(LAZYOS)`, never
`PLATFORM(PLAYSTATION)` (patch `0003`, regenerated by
`tools/webkit/gen_platform_patch.py`). A change to a patch already applied
re-extracts the tree and rebuilds everything; a new patch at the end only
applies. See [`webkit/README.md`](../../webkit/README.md) and
[`docs/webkit-port-plan.md`](../webkit-port-plan.md) §5 W4.

```bash
python tools/webkit/deps.py && python tools/webkit/port.py   # Docker
python tools/webkit/port_run.py --accel auto                 # boot and judge
python tools/webkit/test_port_judge.py
```

**Two checkouts must not build WebKit in the same Docker volume** (each re-extracts the tree and
rebuilds everything, and the build can fail half way): set `LAZYOS_JSC_VOLUME=<name>` for one of
them (`webkit/README.md` says how to keep the caches).

## LazyWeb+ (`LAZYOS_LAZYWEBPLUS=1`, `os.lazy.lazywebplus`)

The web browser, a **plain xui app and a client of webd** ([`docs/lazywebplus.md`](../lazywebplus.md), issue #835;
webd plan P4, [`docs/webd-plan.md`](../webd-plan.md) "P4 as built"). The binary `xui-lazywebplus` is
`xui-app/webplus` (`xui-webplus`: a menu bar, toolbar, status bar, history, downloads, internal pages and
hand-offs), built by `python tools/xui/build.py` into `target/xui/xui-lazywebplus.elf`; it links no WebKit, no curl
and no OpenSSL. Its page is **one full view** of webd (`os.lazy.webd.view.v1`) made through the browser scope
(`os.lazy.webd.browser.v1`) in webd's `browser` profile (`$HOME/.apps/os.lazy.webd/profiles/browser`: cookies,
cache, site storage, the content-blocking store). `xui-app/crates/webkit-remote` (`RemoteEngine`) implements the
`xui-webkit` seam's `Engine` (`xui-app/crates/webkit`: engine trait, mailbox, page view, host-tested against a
recording engine) over `xui_webd_client::FullWebView`; frames go from webd's slots straight into the mailbox. The
C++ engine host that LazyWeb+ used to be (`lazywebplus-app`, `tools/webkit/app.py`, the seam's C ABI) is gone: the
engine, its processes and their sandbox are webd's (`app:os.lazy.webd/webprocess|networkprocess`), and LazyWeb+'s
package keeps only `[processes.listupdate]` (`curl` fetching the ad-block lists). Navigation policy is the
client's (**a page's script can never start another program or run a browser command: only a user gesture can**,
`policy.rs`; webd holds such navigations with `Handoff.Ask`), downloads go to `$HOME/Downloads` through `.part`
files named by webd, JavaScript dialogs are drawn as xui dialogs. Only a `LAZYOS_LAZYWEBPLUS=1` image ships it
(`run_demo.py --lazywebplus`, the launcher's Simple tab): it needs the desktop, the network stack and webd (an
unset `LAZYOS_WEBD` counts as `1`, `LAZYOS_WEBD=0` is an error), and the run sets the big-app profile, a 1 GiB OS
volume, 4 GiB of RAM and an 8G user memory quota. It registers `http`, `https` and HTML files and is the default
browser; which of two browsers `mimed` would open is the user's choice (`user/<uid>/mimed/default/<type>`,
Settings > Default apps, `deskmenu::defaults`), install order otherwise. The engine's processes are sandboxed
(#836: `docs/architecture/process-sandbox.md`); attack them with `python tools/webkit/attack_run.py --browser --app
lazywebplus`. The bundle's SQLite is built without WAL (no file-backed `mmap`: the cookie jar never opened
otherwise). The window crates are declared `GPL-2.0-only OR GPL-3.0-or-later` and the program is distributed as
GPL-3.0-or-later (it links `xui-webkit-remote` and `xui-webd-client`); only link GPLv2-compatible crates into the
window: `python tools/nettls/licenses.py --lazywebplus` and `python tools/webkit/licenses.py`. Upgrading from the
in-process browser keeps `history.tsv`, `notify.tsv` and the ad-block lists; the old engine's cookies, cache and
site storage are not migrated. Known limits: `file:` URLs do not open and there are no tabs.
`python tools/webplus/run.py` builds the image, boots it (the second boot finds the first's history and cookie)
and judges the browser's markers (`WEBPLUS:*`), the engine's (`WEBD:NOTE:<line>`), the host's request log, the OS
volume and the screenshots; `--label-trace` fails on any `LABEL:DENY` beyond the nine optional ones of #836.
The harness boots four times: a third and a fourth boot judge the ad blocker (below), and a run needs
`LAZYOS_TLS=1` (`target/nettls/fetch.elf`), which `--lazywebplus` brings. The stand-in sites
(example.com, a 90s-style theoldnet.com with pictures, cookie, download and test pages), the run's test CA
and the picture encoders are shared in `tools/webtest/` ([`tools/webtest/README.md`](../../tools/webtest/README.md);
`python tools/webtest/test_sites.py`).

A page's **Notifications API** works (#839, `xui-app/webplus/src/notify*`): webd keeps the profile's decisions
and, for a view made with `notify_in_client`, hands the page's notifications to the browser (`NotifyShow`), which
asks once per site with a bar (`notify.tsv` in its folder, told to webd each time a view is made), posts toasts
titled with the site's host, never its own words, at Info, under a per-site limit, and answers `NotifyState`; a
click raises the window (display `ActivateApp`) and runs the page's handler or reopens the page. Every call of
the shell's notification service is made from the window's thread (the process's first). In "page data in memory"
mode (File menu) webd refuses notifications and content blocking. `python tools/webplus/notify_run.py` is its
harness.

```bash
python tools/webkit/deps.py && python tools/webkit/port.py --only WebProcess NetworkProcess webd-app && python tools/webkit/webd.py   # Docker: webd and the engine processes
python tools/xui/build.py                                                                         # the browser (and the other apps)
python tools/webplus/run.py --accel auto                                                          # boot four times, judge
python tools/webplus/notify_run.py --accel auto                                                   # web notifications, boot twice, judge
python tools/webplus/hang_run.py --accel auto                                                     # a page that hangs: the bar, Wait, Reload, Stop (#862)
python tools/webplus/test_judge.py && python tools/webplus/test_notify_judge.py && python tools/webplus/test_hang_judge.py
cargo test --manifest-path xui-app/Cargo.toml -p xui-webplus -p xui-webkit -p xui-webkit-remote
```

**The ad blocker** (issue #845, [`docs/lazywebplus.md`](../lazywebplus.md) "Blocking ads"): WebKit content
extensions (on in `OptionsLazyOS.cmake`; patches `0018` and `0019`), `xui-app/crates/adblock` (Adblock Plus lists
to WebKit rule lists; strict: one pattern WebKit refuses fails a whole list), `xui-app/webplus/src/blocker/`
(settings in `confd`, the list worker, `about:blocker`) and a `curl` child under
the `listupdate` label. The rules compile into webd's `browser` profile (`BlockingCompile`, `BlockingLoad`) and the switch and the
site exceptions reach webd as `SetBlocking`. The filter list is fetched at runtime and never committed or shipped. Check a
converter change against the real engine, not only the tests: `python tools/webkit/blockcheck.py --list
FILE` (the port's `webkit-smoke` in rules mode; needs the build volume of `tools/webkit/port.py`).

```bash
cargo test --manifest-path xui-app/Cargo.toml -p lazyadblock       # unit, conversion, differential, fuzz
FUZZ_CASES=100000 cargo test --manifest-path xui-app/Cargo.toml -p lazyadblock --release
python tools/webkit/blockcheck.py --list easylist.txt              # compile it with WebKit (Docker)
python tools/webplus/test_blocker_judge.py                         # the harness's judge fails when it should
```

The web harnesses bind host ports 80/81/443, and Windows lets a second process bind a port that is already
listening: two harness runs at once (two agents) silently corrupt each other (certificate errors, an empty
request log). Check `netstat -ano | grep "127.0.0.1:443 .*LISTENING"` before a run.

## webd (`LAZYOS_WEBD=1`, `os.lazy.webd`)

`webd` is the per-session daemon that owns WebKit and serves **light views** to other apps over Messenger
([`docs/webd.md`](../webd.md), plan [`docs/webd-plan.md`](../webd-plan.md), P2): an app hands it HTML
(`LoadHtml`) and gets pixels back in shared slots; a light view has no network, no storage, locked navigation
and scripts off unless asked. **Full views** (`idl/webd.midl`, `os.lazy.webd.view.v1`, served as
`app.os.lazy.webd.view`, P2 slice 3) are what a browser needs; what a view may reach is the interface its
`CreateView` came through, which the kernel checks against the manifest: `os.lazy.webd.view.v1` alone has no
network, `os.lazy.webd.net.v1` loads http(s), `os.lazy.webd.browser.v1` adds the `browser` profile on disk,
downloads, content blocking and hand-offs. The shared methods keep the light interface's ids and shapes
(`python tools/webd/test_idl.py`). The light interface is `idl/webd_light.midl` (served as `app.os.lazy.webd.light`), the
portable service `xui-app/crates/webd` (`xui-webd`, host-tested against an in-memory fabric), the engine half
`webkit/port/webd/abi.cpp` over `webd_abi.h` (`webd-abi-test`), and the program `webd-app` joins them:
`webkit/port/webd/main.cpp` (WebKit's run loop on a thread of its own; **the first thread runs the service**,
because `init` and the shell know an app by its first thread) with the Rust static library `xui-app/webd`
(the real Messenger binding, an `eventfd` doorbell, the lifecycle line, a watchdog on WebKit's main thread, the
`WEBD:*` markers). The package `xui-app/packages/webd` is resident and opens with every session of a
desktop image that has built it (`LAZYOS_WEBD` is `1`: required, `0`: left out, unset: shipped when
`target/xui/xui-webd.elf` exists; no network stack; a 1 GiB OS volume; `run_demo.py --desktop` builds it, `--no-webd`
leaves it out, `--webd-demo` adds the demo client): Docs and Mail need it, so every desktop ships it. `python tools/xui/new_app.py` does not apply: it has no window. Same Docker rules as
LazyWeb+ (`LAZYOS_JSC_VOLUME`, never two checkouts in one volume).

```bash
python tools/webkit/deps.py && python tools/webkit/port.py          # Docker, once
python tools/webkit/webd.py                                           # libxui_webd_host.a on the host, the link in Docker -> target/xui/xui-webd.elf
python tools/webkit/port.py --only WebProcess NetworkProcess webkit-views webd-abi-test --run-views --run-webd   # the engine suites
cargo test --manifest-path xui-app/Cargo.toml -p xui-webd -p xui-webd-host    # service and host (pure parts), no Docker
cargo test -p build-support-tests                                     # webd_tests: the switch's requirements
python tools/screenshot/qemu_session.py --image target/lazyos.img --out shots/webd \
    --script tools/screenshot/examples/webd_selftest.json            # the built-in client (Reopen "/selftest"); LAZYOS_UI_PROBE=1 LAZYOS_XUI_AUTOSTART=term
cargo test --manifest-path xui-app/Cargo.toml -p xui-webd-client -p lazydamage -p lazydownloads   # the clients, the shared paint plan and download rules
python tools/webd/run.py                                              # light views end to end (webddemo)
python tools/webd/full_run.py                                         # full views end to end (webdbrowse against tools/webd/full_server.py on 18081)
python tools/webd/test_full_judge.py && python tools/webd/test_idl.py
```

Markers (channel `Webd`): `UP:PASS`, `SERVE:app.os.lazy.webd.light`, `SERVE:app.os.lazy.webd.view`, `VIEW:CREATE client=<label> view=<id>`,
`VIEW:DESTROY view=<id>`, `LOST view=<id> reason=<r>`, `NOTE:<text>`, `QUIT:PASS`, and the self-test's
`SELFTEST:STEP|PASS|FAIL`. A portable crate (`xui-webd`) cannot call `xui_app::trace`: only `xui-app/webd` prints.
The test clients `os.lazy.webddemo` (a light view) and `os.lazy.webdbrowse` (Web View Test: full views
through every scope, logic in `xui_webd_client::browse`, markers `WEBDBROWSE:<STEP>:PASS|FAIL`) ship only
with `LAZYOS_WEBDDEMO=1` (`run_demo.py --webd-demo`).
