# B0: first bare-metal boot of the stick on the Kaby Lake box

Step B0 of [`../../kabylake-box-plan.md`](../../kabylake-box-plan.md). The goal
is not a perfect boot. It is that **whatever happens leaves evidence**: the
box has no serial port you will plug into, so the evidence is photos, the boot
log saved onto the stick, and the survey from Linux.

The SSD keeps Linux throughout. LazyOS writes nothing to it in B0: the stick
is the root (RAM) and `/home`; the AHCI driver does not exist yet, and the PCI
walk only reads.

## 0. Before leaving the dev machine

```bash
python tools/xui/build.py && python tools/abi/busybox.py          # once
LAZYOS_DESKTOP=1 LAZYOS_USB=1 LAZYOS_USB_IMAGE=1 cargo build --release
python3 tools/boot/preflight.py target/lazyos-usb.img             # PREFLIGHT:PASS
python tools/boot/run.py                                          # OVMF, USB only: the judge must pass
```

`preflight.py` re-reads the image's bytes (MBR, the boot FAT's files, a PE32+ x86-64
`BOOTX64.EFI`, `.`/`..` first in each directory, the ramdisk and `lazyos.cfg`,
both ext2 labels). If it fails, do not write a stick.

Write the stick with `tools/boot/write_stick.py` (or `stick_gui.py`); it reads
the image back and compares SHA-256. Keep the digest it prints with the photos.
Use a stick of at least 2 GiB; a USB 2 stick is fine and, on this box, often
the safer choice at power-on (see "if the keyboard is dead" below).

## 1. Survey the box's Linux (10 minutes)

On the box, in its Linux, as root, with the USB stick already in your pocket:

```bash
sudo apt install pciutils usbutils dmidecode efibootmgr ethtool acpica-tools cpuid mokutil
sudo sh tools/boot/survey_linux_box.sh          # writes ./survey-<host>-<date>/ and a .tar.gz
```

Copy the directory to `docs/compat/kabylake/survey/`. It answers, without more
work, questions 2 and 3 of the box plan (audio jack, the Realtek firmware
patch: `08-asound-cards.txt`, `09-nic-dmesg.txt`, `09-ethtool.txt`). Plug a
network cable in first for the ethtool firmware-version field.

Write down, from `02-secureboot.txt` and the firmware setup screen, whether
Secure Boot is on, and note the boot menu key (usually F7, F10, F12 or Esc).

## 2. Firmware settings

Enter the firmware setup (Del, F2 or F10; the survey's `dmidecode` names the
vendor). The settings are those of [`../../usb-stick.md`](../../usb-stick.md):

1. **Secure Boot: off** (or "Other OS"). The loader and the kernel are not signed.
2. **Fast Boot: off**, so the firmware initialises USB before handing over.
3. **CSM/Legacy: leave off.** UEFI is the supported path. If a CSM option is
   on, the stick may appear twice in the boot menu; use the entry that starts
   with `UEFI:`.
4. Write down the firmware version and any "XHCI Hand-off" or "Legacy USB
   Support" options and their values; they decide the keyboard behaviour in
   step 6.

## 3. Boot

Plug the stick into a **rear or direct USB port**, not a hub or a front panel
header. If the box has both blue (USB 3) and black (USB 2) ports, try a black one
first: the first real-hardware run should take the simplest link speed.
Plug a USB keyboard and mouse into the other rear ports. Open the boot menu
and choose `UEFI: <stick model>`.

Take a **photo of every distinct screen**, in order (a phone video of the
first minute works too). Expected sequence:

1. The loader's own progress lines.
2. The kernel's boot text; the `HW:` lines (`HW:FB:`, `HW:TIMER:`, `HW:ACPI:`,
   `HW:I8042:`, `HW:COM1:`) are the ones to capture.
3. The login screen or desktop.

## 4. Reading the outcome

| What you see | Meaning | Capture |
|---|---|---|
| Back to the firmware menu at once, or "not a bootable device" | The firmware refused the stick: Secure Boot still on, a wrong boot entry, or a FAT/EFI file it dislikes | The entry names in the boot menu; the Secure Boot state; run `preflight.py` again |
| Loader text, then a black screen | Kernel entered, framebuffer not usable, or a hang before the display is up | Wait 2 minutes (the ramdisk load is large), then a photo; try once with the stick in another port |
| A red screen titled with the stop reason | The kernel stopped and drew its report (`kernel/src/panic_screen.rs`) | Photograph it **sharp and complete**: the title, the reason and the last log lines are the diagnosis |
| Desktop, keyboard and mouse dead | The xHCI handoff or port bring-up failed | See "if the keyboard is dead" |
| Desktop, input works | B0's main goal met | Continue with step 5 |

### What a good boot looks like

[`qemu-baseline.log`](qemu-baseline.log) holds the markers of a good boot under
OVMF with the stick on `qemu-xhci` (the stick boots to the greeter in about
19 s there under TCG). On the box, expect these to **differ**, and note each:

| Marker | QEMU | On the box, expect |
|---|---|---|
| `HW:FB:` | `1280x800` | the panel or HDMI mode the firmware picked; above 1920x1080 the logical screen is capped |
| `HW:FB:WC:` | `SKIPPED (hypervisor)` | a real attempt to remap the framebuffer write-combining; a slow desktop would point here |
| `HW:TIMER:` | `pit` | `lapic` if the PCH has the PIT gated |
| `HW:I8042:` | `PRESENT` | probably `ABSENT` (no PS/2) |
| `HW:COM1:` | `PRESENT` | `ABSENT` |
| `USBD:XHCI` | vendor `0x1b36`, `handoff=Absent` | vendor `0x8086` device `0x9d2f`, a `handoff=` value other than `Absent` if the firmware owned the controller |
| `DEV:ENUM` | `7 devices` | the 15 functions of the plan's table |
| `HW:ACPI:` | `PRESENT ... hpet=ok` | the same; a `bad_entries` above 0 or a missing table is a finding |

## 5. Save the boot log onto the stick (desktop works)

Open the Terminal. Everything written under `/home` lands on the stick's
`lazyhome` partition and survives power-off; `/` does not.

```sh
mkdir -p /home/user/b0 && cd /home/user/b0
dmesg                 > lazyos-boot.log      # the whole boot log (64 KiB ring)
dmesg | grep 'HW:'    > hw-lines.txt
devctl devices        > devctl-devices.txt   # PCI functions the kernel saw, class, ids
devctl drivers        > devctl-drivers.txt   # what devd matched, and which driver state
devctl rules          > devctl-rules.txt
sync
```

Then photograph the desktop at rest and the System Monitor, and note the
resolution from the `HW:FB:` line. Move
the mouse and type in the Terminal to prove input. Shut down from the menu and
note whether the box powers off (ACPI S5) or stops with the fans still on.

Optional, after those files are saved: `echo test > /home/user/b0/touch` and
reboot to see the stick keep it (`/home` persistence on real USB).

## 6. If the keyboard is dead

The two likely causes are the firmware keeping the xHCI (BIOS handoff) or a
port that needs more time. Try, in order, and note the result of each:

1. A different rear port, with the keyboard alone (no mouse, no hub).
2. A USB 2.0-only keyboard, or one that is not a gaming model with several
   interfaces.
3. In the firmware, turn **Legacy USB Support** / **XHCI Hand-off** from
   Auto/Disabled to Enabled, or the reverse; note both values.
4. Without input there is no Terminal to save the log from. Photograph the
   screen, then boot the same stick on a machine where input works (or
   QEMU) to compare; the `USBD:XHCI` and `USBD:HID:*` lines in the boot log
   are what to look for when the log can be read.

## 7. Getting the evidence off the stick

Shut LazyOS down, plug the stick into the box's Linux (or any Linux), and
find the third partition (`lazyhome`, ext2):

```bash
lsblk -o NAME,SIZE,LABEL,FSTYPE
sudo mount -o ro /dev/sdX3 /mnt        # or: sudo debugfs -R 'ls -l /user/b0' /dev/sdX3
cp -r /mnt/user/b0 docs/compat/kabylake/boot-1
sudo umount /mnt
```

If the OS never got far enough to write, the photos are the evidence. Copy
them to `docs/compat/kabylake/boot-1/` with names like `01-loader.jpg`,
`02-kernel.jpg`, `03-stop.jpg` and one `NOTES.md` of what you did.

## 8. Fill the report

- A row in [`../hardware.md`](../hardware.md): framebuffer mode, the `HW:*`
  verdicts, input result, outcome.
- One line each under the box plan's questions: audio jack, firmware patch,
  and (new) the firmware's USB options.
- An issue for every failure, with the photo, the exact settings, and the
  stick's SHA-256.

## Pitfalls the harness cannot see

- **Wrong disk written.** `write_stick.py` lists removable disks only and asks
  twice; with Rufus or Etcher, pick *DD Image* mode and check the target is
  the stick and not the SSD.
- **A stick that is slow on this box.** The UEFI loader reads the ~100 MiB
  ramdisk through the firmware's USB driver; a cheap stick can take a minute
  on bare metal where QEMU took seconds. Wait 2 minutes before judging.
- **Secure Boot "Other OS" on some boards re-enables itself** after clearing
  CMOS or updating the firmware.
- **The SATA SSD is untouched in B0.** If anything in LazyOS appears to want
  `sda`, stop and report it: the kernel has no AHCI driver and should never
  write to it.
