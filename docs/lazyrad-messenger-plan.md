# Messenger APIs in LazyRAD

**Goal.** A LazyRAD form script can use every Messenger service that makes sense
from a script, the way a VB6 program used COM objects: call methods, react to
events, and answer calls, with readable names, documentation and no wire
details. The API is generated from `idl/*.midl`, so a new or changed interface
becomes available to LazyRAD apps by regenerating, never by hand-written glue.
A packaged app gets the permissions its scripts need without the author listing
them.

```rhai
fn form_load() {
    theme_label.text = sys::confd::get("sys/ui/theme").str_value;
    sys::confd::on_changed("sys/ui/#", |event| {
        theme_label.text = "changed: " + event.payload.path;
    });
}
```

This plan builds on [`rhai-plan.md`](rhai-plan.md) (R3: the `msg` module) and
[`lazyrad-plan.md`](lazyrad-plan.md) (P6: LazyOS modules in the LazyRAD runtime).

## 2. Design

### 2.1 Generated API modules (`midlc --rhai-api`)

`midlc` gets a backend that writes one Rhai source module per interface
(`libs/rhai-lazy/api/<alias>.rhai`) and a Rust index of them
(`libs/rhai-lazy/api/index.rs`). Both are committed, regenerated by one
command and checked by CI like the existing `--out` and `--schema` outputs.

- **Namespace.** Every module is a sub-module of `sys`: `sys::confd`,
  `sys::healthd`, `sys::messenger_topics`. The alias is the interface name
  without `os.lazy.` and `.vN`, dots folded to `_`. `midlc` refuses two
  interfaces with the same alias. One parent namespace keeps the
  global namespace clean: a project module called `confd` cannot collide.
- **Methods.** `sys::confd::get(path)`: the snake_case method with its IDL
  parameter names, a doc comment copied from the IDL and the signature in the
  doc. The body is one line over the dynamic layer
  (`msg::connect(INTERFACE).invoke("Get", [path])`), so the wire behaviour, the
  value mapping and the errors are exactly `msg`'s (`docs/rhai/msg.md`).
  `sys::confd::connect()` returns the `Service` for the generic forms.
- **Structs.** `sys::confd::new_value()` returns a map with every field at its
  zero value, so a script fills a struct without guessing field names.
- **Enums.** `export const` values with the variant names
  (`sys::messenger_topics::QOS_RELIABLE == "Reliable"`).
- **Topics.** For `topic "system/confd/changed/{path...}" : Change`, the
  helper name drops `system`, `events` and the alias from the literal segments
  (`changed`), and `midlc` falls back to the full suffix on a clash:
  - `sys::confd::CHANGED_PATTERN` (`"system/confd/changed/#"`);
  - `sys::confd::changed_topic(path)` builds a concrete name;
  - `sys::confd::on_changed(handler)` and `on_changed(path, handler)` subscribe
    with the declared QoS and run `handler` with the decoded payload;
  - `sys::confd::subscribe_changed(...)` for the pull form (`sub.next()`);
  - `sys::confd::publish_changed(path, change)`.
- **Not generated:** methods whose request transfers kernel objects (channels,
  buffers, rings; `display`, `audio`, `input`, `net` drivers). A script cannot
  create those. The module lists them in a comment instead of offering a function
  that always fails.

The modules are compiled once per process and shared by every engine (the
player builds one per form), so the parse cost is paid once. A generated module
calls `msg::*` at run time, so it runs in the calling engine's `msg`. Each
engine's `msg` knows which form owns it (2.2).

The index also carries, per module, its interface and each topic helper's
pattern. That table drives permission derivation (2.3), so the names a script
uses and the permissions it is granted come from the same generated data.

### 2.2 Events in a form: a window-driven pump

A form cannot call `msg::run()`: it would stop the window. Instead the window
drives Messenger from its own timer:

- **LazyRAD seam (upstream, va1erian/lazyrad).** Two additions next to
  `extensions::add`, neither of which knows about LazyOS:
  - `extensions::add_scoped(|engine, scope|)`: like `add`, plus the form the
    engine scripts (`scope.form`), so a host can attribute what a script
    registers to its form.
  - `extensions::add_event_source(Rc<dyn EventSource>)`: something outside the
    window with script work to do. While a form has work (`active(form)`), its
    window runs a timer (`interval_ms`); each tick calls
    `poll(form, call)`, where `call` runs a Rhai function pointer in that form's
    engine and AST. Errors the source hands back are shown like an event
    handler's error (a message box; the program keeps running). When the
    window closes, `release(form)` drops what the form registered.
- **rhai-lazy.** `msg::install_hosted(engine, fabric, owner)` binds an engine's
  `msg` to an owner. `msg::on` and `msg::serve` record their owner, and
  `Fabric::pump(owner, budget, call)` runs ready work without blocking. Topic
  pulls use the kernel's poll deadline (`EXPIRED_DEADLINE`: answer now or time
  out). Served endpoints are polled the same way. The same work items back
  `msg::run()` for the `rhai` command, so both paths answer services, ack
  reliable topics and turn thrown values into structured errors identically.
  In a hosted engine `msg::run()` is an error that says events arrive on their
  own.
- **lazyrad-os.** `messenger::install()` registers `msg` through `add_scoped`
  and a `MessengerEvents` event source over the shared fabric.

### 2.3 Permissions of a packaged app

An installed app runs under kernel rules compiled from its manifest
(`docs/packages.md`, "What a manifest compiles to"), so the package must
declare what its scripts use:

- `rhai_lazy::msg::permissions::derive(scripts)` scans the scripts' tokens:
  `sys::<alias>::...` names the alias's interface. A topic helper adds
  `subscribe:`/`publish:` with its declared pattern. String literals passed to
  `msg::connect`, `msg::on`, `msg::subscribe` and `msg::publish` add their
  interface or topic. A name built at run time cannot be seen; the docs say so
  and the consent screen shows what was derived.
- **LazyRAD seam (upstream).** `Platform::script_permissions(scripts)`
  (default: nothing), and `PackageRequest::permissions` carries the result
  into the manifest next to the packager's own `os.lazy.display.v1` and file
  rules. Make LazyOS App asks the platform; LazyOS answers with `derive`.

### 2.4 Out of scope (said plainly in the docs)

- Methods that transfer channels, buffers or rings.
- Serving from an *installed* app: the manifest grammar has no permission to
  register a name, so `msg::serve` works for a development run (the IDE's F5,
  the Terminal) and is refused under an installed app's rules.
- Completion in the IDE's code editor (LazyRAD has none yet). The generated
  `.rhai` modules and `libs/rhai-lazy/api/README.md` are the reference.

## 4. Risks

| Risk | Mitigation |
|---|---|
| Parsing ~25 generated modules slows player start-up under TCG | Compiled once per process and shared; measured on the host in a test, which fails above a budget |
| Polling many subscriptions each tick costs syscalls | Timer runs only while the form has sources; one poll call per source per tick |
| A topic handler that fails on every event floods message boxes | The pump reports a source's error once per form and handler, then counts repeats on stderr |
| Two repos move together (LazyRAD seam + LazyOS) | LazyRAD changes are additive; `lazyrad-os` pins the branch head until the upstream PR merges, then the merge commit |

Findings while building it:

- `lazyrad-os` did not build on `main` before this work: #522 moved LazyOS to
  xui `4c2a4fb` while the pinned LazyRAD still used `7e31d5d`, so two
  `xui-core` crates met in one graph. The LazyRAD branch moves to `4c2a4fb`.
- The kernel's poll deadline (`EXPIRED_DEADLINE`, `kernel/src/ipc/channels.rs`)
  is what makes a non-blocking topic pull possible: `NextEvent` is answered if
  `messengerd` can do so in its current turn, else `ETIMEDOUT` at once.
- `lrplay.elf` grows by about 0.5 MiB (5.3 to 5.8 MiB): the schema table, the
  `msg` module and the generated module sources.
